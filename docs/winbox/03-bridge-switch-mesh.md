# Bridge, Switch and Mesh Menus

Covered bridge policy windows: **Bridge → Filters** and **Bridge → NAT**.

## Bridge → Bridge

**Purpose:** create a Layer 2 broadcast domain and optionally a VLAN-aware
software/hardware-offloaded switch.

The list shows name, MAC, protocol mode, root/bridge ID, VLAN filtering and
running state. New Bridge fields are grouped into **General**, **STP** and
**VLAN**-related properties: name, auto/admin MAC, MTU, protocol mode
(`none`/STP/RSTP/MSTP), priority, ageing time, forward/max-message/hello timers,
IGMP/MLD snooping, DHCP snooping, fast-forward, VLAN filtering, EtherType and
frame handling options. Change timers only with a topology reason.

Create the bridge with VLAN filtering off, add ports and VLAN table, build the
CPU/management path, then enable filtering last in Safe Mode.

## Bridge → Ports

**Purpose:** attach interfaces to a bridge and define their STP/VLAN ingress
behavior.

New Port includes `Interface`, `Bridge`, `PVID`, frame types, ingress filtering,
edge/point-to-point/discovery, path cost/internal path cost, priority, horizon,
BPDU guard, restricted role/TCN, broadcast/multicast/unknown-unicast flood and
hardware-offload controls where supported.

`PVID` classifies untagged ingress; it does not by itself authorize VLAN egress.
`H` proves hardware offload. `I` commonly means inactive. Before editing a live
management port, confirm bridge CPU and VLAN membership.

## Bridge → VLANs

**Purpose:** declare which VLAN IDs may leave each port tagged or untagged.

New VLAN contains `Bridge`, one or more VLAN IDs, `Tagged`, `Untagged` and
comment. Dynamic rows can be generated by PVID. The bridge name is the CPU port:
include it tagged when a VLAN interface on the bridge provides routing or a
router service. Avoid assigning one access port untagged to multiple VLANs.

Verify Current Tagged/Untagged, not only configured columns, and capture both
trunk and access sides.

## Bridge → Hosts

**Purpose:** show the forwarding database (learned/static MAC → VLAN/port).

Rows expose MAC, VID, on-interface, bridge, local/external/dynamic flags and
ageing. A dynamic host row is evidence of source learning. Do not delete it as a
permanent repair; correct the source port, VLAN or loop. Static hosts can be
created only for a deliberate forwarding requirement.

## Bridge → MSTI and MST Overrides

**Purpose:** map VLAN groups to Multiple Spanning Tree instances and tune root/
port behavior per instance. Create MSTI with instance identifier, VLAN mapping
and priority; use port overrides for internal path cost/priority. All switches
in a region must share compatible region name, revision and VLAN-to-instance
mapping. A digest mismatch creates a boundary.

## Bridge → Filters and NAT

**Purpose:** bridge firewall filters Layer 2 frames; bridge NAT can rewrite
selected MAC-layer fields. Windows resemble IP firewall lists with rule order,
match fields (interfaces, MACs, EtherType, VLAN, packet marks) and Action tab.
These rules can disable hardware offload or push traffic to CPU. Do not use them
as a substitute for correct VLAN membership.

## Bridge → MDB and Port/Bridge status

The multicast database shows group membership learned by IGMP/MLD snooping.
Bridge and port status expose root ID, root port, topology changes, role, state,
designated bridge/port, path cost and timers. Use status to explain why a link
is forwarding or discarding; never disable STP merely to clear a blocked state.

## Switch

**Purpose:** expose model-specific switch-chip configuration—ports, VLAN table,
ACL/rules, host table and chip registers/features. It may be absent or radically
different because modern configurations often use bridge hardware offload.

Before using Switch:

1. identify exact RouterBOARD model and switch chip;
2. read its block diagram and RouterOS feature table;
3. determine whether Bridge VLAN Filtering is the supported configuration path;
4. verify CPU port, VLAN mode/header and hardware counters;
5. load-test and watch CPU/profile.

Do not copy a Switch-menu VLAN recipe across models. A property available on one
chip may be ignored, invalid or CPU-switched on another.

## Mesh

**Purpose:** legacy HWMP+ Layer 2 mesh (`/interface mesh`), not a synonym for
modern multi-AP Wi-Fi roaming.

The Mesh list creates an interface with mesh portal/reannounce/ageing and MAC
learning parameters. The Ports window attaches Ethernet/wireless/mesh-facing
interfaces and controls hello/flood behavior. FDB shows learned mesh paths.
Use only where the legacy design is understood; routed wireless backhaul or
current CAPsMAN/WiFi design is normally easier to contain and troubleshoot.
